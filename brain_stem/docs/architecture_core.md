**Document version:** 2026.10.04.Absolute-Core
**Status:** Active master source of truth for one installable Stacey model identity and one shared learned graph; prototypes include signed Core-to-scheduler plumbing, Core-generated consent-gated system-fit requests, deterministic `.stacey` bundle builder/verifier, operator-confirmed POSIX writes with FB-004 projection, bounded deterministic modality/data/control services, review-only Core Foundry, and plan-bound optimizer/data-cursor resume. **Runtime boundary:** Local, in-process, platform- and model-provider-neutral

## 1. Purpose and Operating Model

**Stacey is one model identity, one complete learned graph, and one installable model bundle:** a shared backbone/control representation with all declared learned capability paths inside that graph, plus scoped persistent state and deterministic execution authorities. It is not a multi-model operating system or an OS router. The Core is the graph's cognitive control: it interprets context, reasons about system/task state and action consequences, checks whether the declared graph and controls can meet a task, compiles or revises task graphs, selects internal graph paths, and integrates their results with authorized host-tool results. Internal graph parts may be staged or unloaded when idle; the complete bundle need not be resident in GPU memory. The Core does not generate conversational copy or directly perform every task.

The Core is neural cognition; deterministic controls are the embedded execution and safety substrate of the Stacey bundle, not a separate user-facing OS. The substrate enforces authorization, resource admission, internal weight lifecycle, typed contracts, receipts, and action policy. The Canonical World Model Ledger (FB-004) is provenance-bearing persistent state that the Core can query and update; it is not the Core's weights or hidden activations. Model proposals do not become trusted world state until validated and committed through deterministic controls.

### Model Identity and Adaptive Cognition

Stacey analyzes the capability/control needs of a task as part of its own reasoning. Its typed `SystemInspectionDirective` names the purpose, exact probe IDs, required internal graph paths, required controls, and minimum resources; it must be paired with clarification and an empty runnable task graph. The runtime converts it into a pending consent request and invokes no host probe. Only after an operator grants a separate exact-digest `INSPECT_SYSTEM` signature may bounded adapters observe allowlisted host surfaces. The Core receives a typed capability/control inventory, not ambient credentials or unrestricted system access. The current prototype reports system fit, but host orchestration must still carry reviewed evidence into a newly authorized Core ingress before continuing the task. The Core selects graph paths; when vision, audio, coding, temporal analysis, or retrieval is unnecessary, those internal parts remain unloaded or uninvoked.

Self-expansion is an internal model-building capability, not autonomous authority. The prototype `SystemInspectionService` can, after a signed `INSPECT_SYSTEM` grant, compare explicitly requested probes and capability/control needs against typed evidence and the exact active signed bundle; it reports graph-path, control, or measured-resource gaps and performs no host writes or weight loads. Stacey may use approved data and provenance-bearing outcomes to propose a compatible internal graph-part or graph-revision build, then train/assemble and evaluate it within explicit budgets. A candidate becomes part of the active Stacey graph only after independent rights, safety, capability, compatibility, and release approval. Promotion is atomic and rollbackable; an unapproved or failed candidate cannot alter the active model. Third-party lineage remains attached to any integrated internal part. No model output can grant host permissions, sign approvals, or activate its own release.

The design is provider-neutral. Model runtimes, hardware backends, identity sources, and future surface connectors are replaceable adapters, not hard-coded core dependencies. Local laptop, mobile edge, and optional private-cloud execution all belong in the design; local hardware is the first evaluation surface. Cross-surface placement depends on capability fit, measured resources, privacy scope, availability, and latency/cost policy. It is not a fixed model-to-device map.

The current repository is not a trained Stacey graph: it contains a signed-ingress runtime prototype that still leases independent artifacts by capability (a known topology mismatch); deterministic workspace actions and provenance projection; bounded visual, audio, structured-data, temporal, relational, volatility, and response services; a review-only scratch-Core Foundry; and plan-bound optimizer/data-cursor resume. These are tested prototypes using fixture authorities/backends. There are no trained shared-backbone or internal capability weights, rights-cleared real corpus, protected human-reviewed holdout, broad pretraining backend, production key provisioning/revocation, production approval services, qualified Android NPU adapter, or private-cloud runtime.

The system is intended to expand across reasoning/planning, coding, document and data work, multimodal interaction, communication, and authorized actions. "Everything imaginable" is an extensibility goal, not a guarantee that any finite model set solves every task. Each capability claim must be demonstrated by task-specific evaluation.

## 2. Taxonomy and Implementation Status

Stacey is one learned model graph with one stable model identity. Block 0 is its shared backbone and cognitive control; Blocks 1–12 are declared learned graph paths/heads/parts or deterministic typed interfaces that operate on the graph's common representation, while Blocks 13–15 are deterministic control/backend functions. Weight shards may be stored and mapped separately, but they are never independent model peers selected by an OS-style router. The 8 cognitive layers describe overall computation; the 15 blocks refine internal functions and host interfaces, not standalone model processes. Versioned candidates are complete graph revisions or compatible internal-part revisions. The current byte-level Core and per-capability artifact lifecycle are scaffolds/prototypes; supplied sizes, shapes, and hot-swap claims are unverified targets, not the selected production topology.

### Eight Cognitive Layers

These are functional stages, not a requirement to train exactly eight models:

1. **Sense:** internal modality paths turn authorized image, audio, and other inputs into typed observations in Stacey's shared representation.
2. **Understand:** the shared Core interprets intent; any useful specialized representation is an internal graph path, not a second learned router.
3. **Reason:** the Core builds hypotheses, handles ambiguity, predicts consequences, and creates/revises dependency-aware plans.
4. **Act:** the learned graph proposes typed operations; deterministic host services authorize, stage, commit, and receipt them.
5. **Internal capability graph:** conditional graph paths handle coding, extraction, critique, language, and future domains under one shared model identity.
6. **Memory:** deterministic scoped stores preserve facts, episodes, artifacts, and provenance; learned retrieval/ranking may assist but cannot silently rewrite canonical state.
7. **Orchestration:** the Core chooses internal graph paths; deterministic admission enforces resource budgets, isolation, and graph-part lifecycle.
8. **Execution tools:** deterministic permissioned interfaces act on the local or explicitly authorized external environment.

#### Build Order to Charter-Complete Stacey

1. **Freeze the charter-derived capability contract:** Blocks 0–15 and Surfaces A/B/C are the plan scope; enumerate the accepted task, modality, file-format, action, identity, privacy/retention, and resource envelopes for each block/surface in versioned contracts. Block 15 remains explicitly optional and must have a measured include/defer decision. Convert each charter requirement to an acceptance case before selecting production models.
2. **Complete the deterministic perimeter and graph skeleton:** trusted authorization, measured resource providers, canonical world-state ledger, staged local mutation/compensation for v1 tools, crash recovery, sandbox, complete graph/part manifest, tensor-port validation, and internal graph-part lifecycle. Keep learned outputs non-authoritative.
3. **Complete the training/evaluation inputs:** owner-provided training hardware profile, approved rights-cleared corpus, trusted human review/approval, protected holdout storage, and leakage/contamination checks. Finalize the model/tokenizer/config and train/evaluation manifests against those inputs.
4. **Train the complete graph candidate:** train the frozen shared backbone and declared internal paths, using rights-cleared scratch pretraining for any broad language/code claim and task/path objectives for the full capability constitution. If broad pretraining data or compute is unavailable, restrict claims to measured scope. Evaluate the graph on protected holdout and calibrate thresholds; do not promote the random scaffold based on plumbing tests.
5. **Integrate and harden the first learned paths:** run the one graph runtime, strict parse, scope/path/DAG/confidence validation, live admission, internal subgraph execution, result verification, receipt, and recovery through real local adapters.
6. **Expand by evidence:** revise or train compatible internal graph parts for measured failure clusters, one path at a time, then jointly evaluate the complete graph. Add vision/audio/retrieval/mobile/cloud only within the frozen topology/contracts and with provenance and acceptance gates.
7. **Surface A release:** qualify the full required graph paths, tools, internal-part lifecycle, recovery, package and protected evaluation on a named laptop/host profile. Surface A is not whole-system completion.
8. **Surface B mobile edge:** implement a device-specific runtime/processor adapter for the same Stacey graph identity, with an approved compact graph revision/quantization, authenticated scope-bound updates, internal-part residency/power management, offline behavior, privacy controls, and rollback; test on named supported devices and NPUs.
9. **Surface C private cloud:** implement a separately authenticated private deployment of the same approved Stacey graph identity/revision, with encrypted/minimized context transfer, explicit user/tenant authorization, network failure/cancellation, local result validation, receipts, and deletion/retention controls. Cryptographic secrets remain in host security components; they are never passed to model input.
10. **Governed Foundry:** implement candidate generation/training orchestration as a bounded, auditable job system that can build and evaluate graph revisions from approved data, bind each graph/part to source/config/run digests, and submit passing candidates for human approval. It may not self-approve, self-deploy, silently import outside weights, or alter the active graph.
11. **Full charter release gate:** all mandatory Blocks 0–14 have implemented internal graph paths or explicitly designed deterministic host services per their contracts; Block 15 is implemented or formally deferred with evidence; the complete graph passes protected path/ablation and end-to-end suites; A/B/C deployments pass security, privacy, failure/recovery, resource, and rollback gates; and Foundry outputs remain review-gated. Beyond-charter capabilities require new versioned scope and tests.

### Stacey Model Graph: Parts and Lifecycle

The deliverable is **one installable, versioned Stacey model bundle with one model identity and one complete learned graph**. Its internal weight parts may be modular and dynamically resident, but users install and invoke Stacey as one model; deterministic lifecycle/safety machinery is subordinate substrate, not an OS router or competing agent. The bundle binds the shared backbone, all approved internal graph parts/adapters, shared state interfaces, capability contracts, deterministic safety substrate, and release manifest. The Core owns understanding/reasoning/planning/path selection and decides which internal graph paths to activate. Some functions may remain deterministic host services when learning adds no measured value.

#### Complete Model Constitution and Pre-Training Gate

The shared Core must be trained to operate the **complete Stacey graph constitution**, not merely a blank prompt or an imagined collection of future modules. Before production training begins, freeze the full graph/path roster, typed ports and results, capability-to-node/part mapping, system-inspection/consent protocol, resource/residency policy, release schema, and failure behavior for Blocks 0–15 and Surfaces A/B/C. A graph path may be marked unavailable until its internal weights and tests are qualified, but the Core must understand every path's purpose, contracts, required controls, activation request, and missing-path behavior. No fake part is exposed as available.

**One identity, multiple internal component kinds:** the installed identity is `stacey`; each active signed `StaceyModelBundleManifest` identifies one immutable model composition and binds its embedded graph-topology manifest. Its component inventory must support these signed component kinds:

Each release maps every capability ID to a declared internal graph path (one or more node/part IDs and typed ports) or to an explicitly approved deterministic host implementation. The binding covers the complete graph and part-manifest digests, contract/schema digest, dependencies, required controls, modality assets, and measured resource envelope. A portable `.stacey` bundle carries the signed release, graph and selected part manifests with exact bytes, compatible runtime package/dependency lock/SBOM or a verified installation reference, and platform-adapter requirements. The current archive builder packages active-release model bytes and verifies component signatures; it is not yet a complete installer, does not include the runtime/SBOM, and does not implement update/rollback installation.

**Core knowledge versus deployment inventory:** train the shared Core on the stable capability ontology, graph-path contracts, and controls, not on filesystem paths, model brands, or a fixed active-part roster baked into weights. At runtime the host supplies the verified active-release graph inventory (capability ID, internal node/part IDs and digests, contract, availability, modalities, controls, and resource profile). The Core may request an internal path or an inspection probe; the deterministic host resolves that request only to nodes in the one signed Stacey graph. Thus the model knows its complete body while remaining correct when a surface-specific graph revision omits, replaces, or unloads a part.

**System-fit and expansion loop:** a task that requires unknown host context may produce a typed `SystemInspectionDirective` containing purpose, bounded probe IDs, required internal graph paths, required controls, and minimum resource requirements. The runtime pauses and presents that exact request for operator consent. Only a separate signed grant for the exact request, scope, and active release permits allowlisted read-only probes. The host then creates a fresh, provenance-bearing Core ingress with accepted evidence; the Core decides whether the active graph fits, asks for information, or returns a graph-path/control gap report. A gap report may be submitted to the Foundry as a candidate graph-part/revision request; it cannot install weights. The current prototype implements consent pause and fit report separately, but not evidence-to-new-ingress continuation or Foundry handoff.

**Dynamic residency is an internal model policy:** the `.stacey` bundle is not mapped in full. Graph-part bytes may remain on disk, be staged in bounded host memory, or be mapped to CPU/GPU/NPU only for a needed graph path. The Core receives measured graph/resource state, requests internal path IDs, and remains subject to deterministic byte reservations, graph leases, exact revision pinning, cancellation, and confirmed unmapping/quarantine. Unneeded parts are not invoked; no policy assumes the entire graph fits GPU memory. If measured capacity cannot support the shared state and required path, the selected backend must provide a safe measured offload/paging policy or Stacey declines the task; it must not become an OS-level model router.

#### Planned Complete Graph Roster

The table below is the complete functional constitution of one graph plus its deterministic host boundary. It is not an ensemble of independent models. Every learned block is implemented as a graph path/head/encoder/decoder sharing the graph's declared representation, token/state contracts, and control context; internal shards may be mapped separately but have no independent model/runtime identity. The backbone and all declared paths are trained under one topology-aware plan, though path-specific objectives or compatible part revisions may be staged separately. #### Canonical Stacey Graph Layout

The frozen graph is one end-to-end computation with one parameter namespace, tokenizer/state contract, execution context, and model identity. Its conceptual dataflow is:

1. **Typed ingress boundary:** deterministic adapters authorize and bound text, image, audio, structured data, ledger assertions, scope, and resource state. Secrets, permissions, raw unbounded files/logs, and mutation handles never enter the learned graph.
2. **Internal modality stems:** text uses the shared Stacey tokenizer/embedding contract; visual, audio, temporal, and structured inputs use declared internal encoders/projections that emit typed tensors into the same shared representation. These are graph subgraphs, not model-serving endpoints.
3. **Shared cognitive backbone (Block 0):** a common transformer/state-processing trunk maintains the request's learned context and provides the representation used by understanding, reasoning, planning, consequence prediction, and result integration. Exact architecture/size are selected only after W0 topology is frozen and hardware/data are measured.
4. **Conditional internal paths (Blocks 1–12):** typed graph nodes consume shared state and declared inputs, then return typed results to shared state. Blocks 2/3 are shared-backbone heads/paths; sensing, temporal, audio, critique, retrieval, code, structured extraction, action proposal, and response are conditional subgraphs. Nodes may share parameters, but every capability ID resolves to an explicit graph path and exact port contract. No path has its own tokenizer/controller/request authority or standalone inference process.
5. **Core-controlled iteration and integration:** the shared cognitive state can select a path, consume its result, revise the task DAG, and invoke another path within budget. The deterministic graph executor performs only requested registered nodes and enforces dependencies/resources; it does not choose a separate model or replace learned cognition.
6. **Typed model outputs:** the graph emits a validated-decision proposal, internal path plan, clarification directive, or response content. It cannot authorize, sign, commit, execute code, or mutate canonical memory. Deterministic validators and host authorities make those decisions.
7. **Deterministic substrate and persistent state:** Blocks 13–15, scope/permission checks, FB-004 ledger, receipts, tool execution, and surface adapters remain signed deterministic components outside trainable weights, but are packaged and version-bound with Stacey. Ledger data enters only through bounded typed reads and provenance references; it is not hidden model state.

Before W4, W0 must freeze the graph adjacency/gating, all node IDs and functional definitions, typed input/output ports and tensor shapes, shared-state/tokenizer rules, path-availability semantics, parameter-sharing boundaries, training objectives and required curriculum coverage, active-subgraph resource accounting, and graph revision/compatibility rules. Numeric dimensions and parameter counts are then selected by measured profiling without changing the frozen functional topology. A missing trained path remains represented in the graph constitution and training target but is marked unavailable at runtime until its exact weights pass evaluation; the Core must be trained on both available and unavailable-path cases.

#### Release and Artifact Manifests

Every cohesive deployment is one `StaceyModelBundleManifest` containing one executable Stacey graph and its signed internal weight parts. The root bundle manifest binds one `StaceyGraphManifest` topology digest; the graph manifest declares nodes, ports, sharing/gating rules, and mappings to signed part manifests:

 - Stacey model identity/version, complete graph/topology digest, signed bundle manifest, approval, and rollback target.
- Exact graph checkpoint/shard digests, architecture and training configuration, shared tokenizer/vocabulary digest, code/data lineage, protected evaluation/calibration evidence, and measured resource profile.
- A capability-to-internal-graph mapping: capability ID -> graph node/part IDs -> typed tensor/input/output ports -> required controls and modality processors. It does not map capability IDs to independently runnable model artifacts.
- Explicit internal part kinds: `SHARED_BACKBONE`, `INTERNAL_EXPERT`, `MODALITY_ENCODER`, `ADAPTER_DELTA`, `TOKENIZER_ASSET`, `PROCESSOR_ASSET`, `DETERMINISTIC_COMPONENT`, `RUNTIME_COMPONENT`, and `SURFACE_ADAPTER`. Only the complete signed Stacey bundle is a deployable model. A part manifest binds graph location, tensor/interface schema, exact base/parent digest when applicable, source/training/license lineage, quantization format, evaluation, and resource profile.
- Third-party weights may enter the graph only when they can be converted/integrated as an internal part with compatible tensor ports, shared tokenization/state semantics, license/provenance, and joint evaluation. A standalone model with its own controller/tokenizer/backend is not a Stacey runtime capability. If it cannot be integrated, it may be a reviewed teacher/reference only where rights permit; train or distill a compatible Stacey-owned part rather than routing it as a peer model.
- Per-part placement and residency: host-staged, CPU-mapped, GPU/NPU-resident, or unloaded. The single graph scheduler owns activation and memory accounting; no part gets its own independent transaction authority or user-facing agent identity.
- Software bill of materials and exact runtime/library versions for the one executable bundle. No arbitrary filesystem scan, ambient model discovery, or remote code execution is allowed.

The current candidate catalog is in-memory and describes whole model candidates; it must be replaced by a durable, integrity-checked graph/part catalog. Core plans name stable capabilities, never filesystem paths or model brands. The deterministic weight-part loader resolves a capability to graph node IDs in the currently active Stacey bundle, checks part digest/parent graph/tensor ports/license/approval and measured byte budget, then maps the required subgraph within the one runtime. An unapproved or incompatible part cannot be selected, and an unavailable capability yields a structured fit gap or clarification rather than a peer-model dispatch.

#### Single-Graph Runtime Interfaces

The code-complete target is one loaded Stacey runtime with internal conditional computation, not one runtime handle per specialist model:

1. `StaceyGraphManifest`: describes one graph identity/revision, shared tokenizer/state protocol, gated graph nodes, typed tensor ports, internal part references, capability/control map, parameter-sharing boundaries, and active-subgraph resource model. Its digest is bound by the signed `StaceyModelBundleManifest`.
2. `StaceyModelRuntime`: loads/executes the shared graph and owns one request context and model identity. Subgraphs/experts may be active, staged, or unloaded, but they cannot dispatch as independent user-facing models or own separate authorization.
3. `WeightPartLoader`: verifies and maps/unmaps internal graph shards or adapter deltas into declared graph nodes. It checks parent graph digest, tensor names/shapes, shared embedding/tokenizer contracts, quantization, license, byte budget, and memory-release confirmation before making a part available to the graph.
4. `InternalCapabilityGate`: maps stable capability IDs emitted by the Core to graph nodes/parts in the active Stacey manifest, checks prerequisites and policy, and exposes a typed unavailable/fit-gap result. It never spawns an independent model or gives the Core filesystem paths.
5. `HostAuthorityBridge`: separate typed and permissioned interfaces for system inspection, local actions, receipts, and ledger updates. These enforce controls but do not become another agent or scheduler that chooses cognition.

The current prototype has a signed-ingress Core facade and sequential scheduler that leases independent `ModelRuntimeBackend` handles by capability. That is useful plumbing but is **not the target single-model topology** and must be retired/replaced in W2 before the weight-layout-ready gate. There are no trained graph weights or production runtime; system-inspection consent currently pauses at a pending request, and host orchestration must still carry reviewed evidence into a new Core ingress. FB-038/FB-004 prototypes exist, but production authorities, end-to-end telemetry, cancellation, and recovery are open.

#### Internal Weight-Part State Machine

`DECLARED -> SIGNED -> COMPATIBLE -> UNMAPPED -> STAGING -> MAPPED -> ACTIVE_IN_GRAPH -> MAPPED -> EVICTING -> UNMAPPED`. One `StaceyModelRuntime` remains the sole model identity across all transitions. The Core or activation policy can request a declared part ID but cannot open a path or alter a tensor. Approval, graph-parent, shape, tokenizer, license, or scope failures never enter `STAGING`. `MAPPED` bytes must be reserved/accounted; `ACTIVE_IN_GRAPH` is protected by graph execution leases. In-flight nodes reach a task boundary before deactivation. Failed or uncertain unloads quarantine the part/device domain and prevent new graph plans from depending on it.

#### Dynamic Weight Pool and Adapter Switching

The self-trained Stacey backbone is the stable model identity and cognitive control. The trainable topology is a versioned Stacey graph: shared layers plus internal expert/encoder/adapter weight parts connected through declared tensor ports and one shared request/control context. A system-fit candidate selects or builds a compatible graph revision and maps capability IDs to internal graph nodes; it does not start sibling model controllers. The Core does not silently rewrite or self-promote weights. Missing capabilities may trigger a bounded Foundry build request from approved data or license-approved sources, but the result must be converted into a graph-compatible internal part, jointly evaluated, and independently approved before activation. Incompatible standalone checkpoints may be reference/teacher inputs only when their terms allow; they are not loaded as runtime peers. All language experts share the bundle's tokenizer/embedding contract unless a modality encoder produces a typed shared representation. Vocabulary changes require a new compatible graph and checkpoint, not a detached token table.

No full-brain-on-GPU assumption is allowed. The single graph runtime stages internal partitions by graph node: shared backbone/state stays resident only when measured capacity supports it, while inactive experts/encoders may remain on disk or in host memory and be mapped only for a selected path. Internal expert activation preserves one request context, one model identity, and shared graph interfaces; it is not a handoff to a separately routed model. If the shared backbone must offload, the same Stacey runtime must preserve the bounded control context and recover at a declared graph/task boundary. Reserve staging capacity in **bytes** for incoming internal parts, activations, and backend workspaces. Multiple internal parts may share capacity only when measured graph execution and overlap policy prove the peak fits; do not count model files or assume simultaneous residency. Load/offload latency, peak memory, and in-flight activation behavior must be measured on each target backend.

When capacity is insufficient, the graph planner computes the approved dependency closure for a capability path, and the single runtime stages only the required internal parts without overwriting active graph state. It verifies parent-graph/port digests, reserves measured bytes, and switches the active subgraph only at a task boundary while preserving the one model identity and request context. Idle internal parts may be unmapped after all graph leases release. Eviction is a deterministic policy over graph dependencies, active executions, measured memory, and configured latency/cost; the Core may request capability IDs but cannot manipulate memory directly. Failed part activation or uncertain release keeps the previous valid graph binding when safe, quarantines the part/device domain, and returns a structured unavailable/resource result or clarification. Every transition is receipt/telemetry-bound to graph revision, part digest, task, backend, allocation, and outcome.

The performance/quality evaluation must compare graph revisions and internal execution plans under one Stacey identity: shared backbone only, backbone plus selected experts, adapter/part revisions on the exact graph, and modality paths on/off for tasks that need/don't need them. Record graph/part cold-start, staging and mapping latency, activation/deactivation, inference, peak host/device memory including staging/activations/KV/workspaces, task quality, failure/rollback behavior, and concurrent graph requests. Remove or disable any internal part/revision that fails capability, safety, provenance, licensing, tensor compatibility, or resource gates.

- **Before graph-part activation:** verify the signed Stacey bundle/graph revision, part digest, parent graph and tensor-port compatibility, source/license approval, capability contract, and resource estimate; reserve measured host/device bytes before mapping the part.
- **During use:** bind each internal graph call to transaction/correlation ID, scope, bundle revision, activated part IDs, and contracts. Enforce shared-state boundaries, timeout/cancellation, context/batch limits, output validation, and mandatory deterministic Block 6/8 gates.
- **Before unmapping:** stop new graph leases to the part, reach a task boundary or apply the explicit cancellation policy, release the backend mapping, and confirm resource accounting. Never unmap an in-flight dependency.
- **On failure:** release only resources proven released. If part unmapping/memory accounting is uncertain, quarantine that graph part/device domain and deny dependent graph paths until reconciliation; do not claim successful cleanup.
- **Graph revision/update:** stage and verify a complete compatible internal graph revision before activation. Switch the one Stacey runtime atomically at a task boundary, preserve the prior signed bundle for rollback, and reject mixed graph/port/contract revisions.

The shared backbone and internal graph parts may remain resident only while the verified target profile can sustain them. Required graph parts are mapped just in time and safely unmapped when idle; no independent specialist process is launched. No latency or hot-swap guarantee is accepted until measured on each supported backend. CUDA, CPU mapping, mobile NPU, and private-cloud backends may have different graph-part lifecycle semantics and require separate integration tests.

### Charter-Complete Stacey Graph Gate

**Code-complete** for the frozen charter means the implementation and training pipelines for every Block 0–15 capability, the complete Stacey graph manifest/runtime and internal-part lifecycle, the required deterministic host authorities, and Surface A/B/C deployment adapters pass integration, failure, and security tests. Tests cover graph-port/shape compatibility, internal path selection, staging-capacity admission, concurrent graph requests, in-flight part protection, measured mapping/offload costs, failed graph-revision rollback, and uncertain-unload quarantine. Test artifacts may be used during development, but a release cannot substitute mock authorities or omit a required graph capability. **Capability-complete** additionally means the single Stacey graph passes protected quality/calibration suites across its declared task families, with capability-specific path/ablation tests and joint end-to-end evaluation. No independent learned specialist is required or permitted as a runtime peer. ### Stacey Core v0 Contract

Stacey Core v0 is **one learned model graph** handling understanding, reasoning, planning, consequence prediction, and internal capability selection. All learned capabilities are nodes/weight parts in that graph, sharing the declared model identity, tensor contracts, and request/control state. The Core may select an internal graph path or request an authorized deterministic host tool; it cannot route to a separate learned model as a capability peer.

The Core receives one schema-validated Unified Context Ingress Envelope containing exactly four data matrices:

1. **Inbound intent vector:** raw user language or a typed upstream event signal. The Core must not receive raw file dumps or unbounded system logs; deterministic host adapters bound, type, and source observations before ingress.
2. **Trusted scope lock:** tenant, user, project, and workspace IDs supplied by the deterministic host. The Core must echo them exactly; it cannot authenticate or change them.
3. **Canonical ledger snapshot:** bounded state assertions, verified facts, current environment state, and provenance references already filtered to the trusted scope.
4. **Graph and resource state:** active signed graph revision, approved internal-part availability/status, current leases, timestamped resource-domain measurements, and registered deterministic host-tool contracts. This state describes one model's available internal paths plus external non-learned authorities; it is not a catalog of peer models.

Before any internal graph path or host tool runs, the Core emits one JSONL Declarative Task Graph Envelope. Required contents:

- Transaction and correlation IDs, `assigned_block_id=BLOCK_0_CORE`, and an internal predicted-consequences summary.
- The unchanged trusted four-field scope vector.
- An acyclic task DAG naming internal graph paths and/or registered deterministic host tools, target block IDs, conditional dependencies, and exactly one per-step resource estimate. Internal paths execute within the same Stacey runtime; estimates are untrusted predictions and deterministic admission checks fresh measurements before mapping parts or granting tool leases.
- A calibrated `confidence_coefficient` in `[0,1]`, where higher means more confident, plus structured clarification reason codes. The host compares it against an injected minimum-confidence policy; below threshold, it refuses internal-path/tool execution unless the output explicitly requests clarification. Calibration is an empirical property, not guaranteed by emitting a number.

The Core output is not user-facing chat, executable code, shell commands, or a direct mutation. Clarification is an action directive with reason codes; the internal Respond path or deterministic templates may phrase it for the user. Before execution, a deterministic validator checks transaction identity, exact scope echo, registered internal paths/host tools and block pairs, DAG acyclicity, resource-estimate coverage, and the clarification threshold. Resource estimates do not grant or reserve memory.

### Staged Model Build Order

1. **Freeze evaluation before training:** author human-reviewed development and access-controlled holdout cases for scope, ambiguity, multi-step DAGs, internal-path selection, estimates, consequences, capability gaps, and context-aware graph revision. Visible fixtures are not holdout evidence.
2. **Assemble the rights-cleared corpus:** target the complete graph constitution, with separate data objectives for shared language competence and task/path behavior. Broad language/code competence requires documented rights-cleared pretraining material; small instruction examples alone cannot create it from random initialization.
3. **Train a tokenizer and random-init text candidate:** compare byte-level against BPE/Unigram tokenizers trained on the approved corpus. Record tokenizer and architecture as part of the weight lineage; do not assume the present byte Transformer is the winning design.
4. **Pretrain then task-train:** use next-token pretraining on approved text/code when broad linguistic competence is a goal, then supervised examples for graph control, internal-path selection, modality tasks, and result integration. Evaluate uncertainty against reviewed labels.
5. **Qualify and package:** compare complete-graph bundle size and active-path host/device memory, quality, latency, throughput, and energy. Serialize safely; bind graph/part digests, config, tokenizer, code, corpus, run, and quantization. Require regression, security, rights/provenance, compatibility, and independent approval before activation.
6. **Grow internal paths by evidence:** choose the next graph gap from protected end-to-end failures. Train a compatible internal part from rights-cleared data or integrate reviewed weights only when they satisfy graph contracts and terms. Evaluate path ablations and the full graph; no learned component is deployed as an independent specialist artifact. One text backbone alone need not cover every modality, but all learned modalities remain parts of one Stacey graph.

No approved training dataset, full pretraining corpus, or production graph is selected by this plan. A bounded supervised task-graph trainer exists, but it is not a broad pretraining system. The shared backbone is intended to remain scratch-initialized; external references are unscored/unapproved and may contribute internal weights only after compatibility, quality, resource, provenance, and terms review. They must never be silently loaded as peer models.

### Training Run Envelope and Readiness Gates

The current environment has not provided a verified accelerator profile. The previously mentioned RTX 4050 with 6 GB VRAM is a provisional planning assumption only; record it as unknown until a probe on the actual training host captures GPU model, total/free memory, driver/runtime, measurement timestamp, CPU RAM, and free storage. Do not infer host hardware from a dev-container configuration. If no usable accelerator is visible, CPU runs are limited to data/loader, tokenizer, forward/loss, and checkpoint plumbing; they are not evidence of practical pretraining feasibility.

Keep inference artifact bands (<=0.4, <=1, <=2, <=3 GB after quantization) separate from training profiles. Full-precision or mixed-precision scratch training also holds gradients, optimizer state, activations, temporary workspaces, and data buffers. A quantized 3 GB inference artifact is not trainable in 3 GB VRAM, and a 6 GB card cannot be assumed to train a model whose quantized inference artifact approaches 3 GB.

If a single 6 GB accelerator is verified, the first trainable pilot is deliberately small: random initialization, 10M-50M parameters as a sweep range, micro-batch 1, and an initial maximum sequence length selected after profiling serialized ingress plus target-length percentiles (start testing around 512-1024 tokens, increase only when measured). Use mixed precision only if the backend supports it reliably; use gradient accumulation and activation checkpointing only after profiling, not as assumed capacity. This pilot tests data plumbing, loss reduction, and narrow task behavior; it cannot establish broad language competence, strong reasoning, or the final Core. Do not try to scratch-pretrain a 0.4-3 GB inference-class model on an unverified 6 GB GPU. Larger candidates require a separately measured training host, memory/cost plan, and privacy review before data is moved.

The first full-data experiment is not ready until the approved corpus and a protected holdout exist. Maintain two purpose-tagged corpora: (A) rights-cleared general text/code for any broad next-token pretraining goal, and (B) human-reviewed four-matrix ingress-to-decision examples for Stacey task-graph supervised training. ## 3. Building Blocks and Control Flow

The `brain_stem/substrate/` package is the Phase 1 composition root and typed contract boundary. `SubstrateKernel` is the light kernel; each implemented block has its own directory under `brain_stem/substrate/blocks/`. The mock worker is separately isolated under `brain_stem/substrate/workers/`. The Phase 2–4 building blocks live under `brain_stem/src/swarm_core/`. Tests exercise them without a server, model download, GPU, or external process.

For `ROUTE_TASK`, the current control flow is:

1. Ingress accepts a typed `Intent` and trusted `authorized_scope`.
2. The kernel requires non-empty `tenant_id`, `user_id`, `project_id`, and `workspace_id` on both scopes and requires exact equality. It also checks the supported action and non-empty transaction ID, correlation ID, and goal. Reject before invoking any worker on failure.
3. Block 2 classifies the intent; Block 3 creates a task plan.
4. The registered in-process CPU mock worker executes the plan.
5. Block 6 validates step uniqueness, the registered mock capability, status, transaction/correlation IDs, and completed steps.
6. Block 8 verifies the plan transaction and returned goal against the original intent.
7. Only after both checks pass does the kernel return an `ExecutionReport` to its in-process caller.

Block 6 always precedes Block 8. There is no network port or output listener. The host invoking the kernel is responsible for obtaining `authorized_scope` from a trusted local identity boundary; comparing two untrusted caller-supplied values is not authorization. The current prototype accepts that trusted scope as an explicit method argument and does not implement identity authentication or a ledger.

The current classifier and decomposer are deliberately small deterministic mocks, not trained models. The current planner emits one `mock.general` step. Unknown capabilities fail closed in Block 6. The worker interface is replaceable without changing the ingress, contract, or validation boundaries.

## 3A. Stacey Core v0 Skeleton

Stacey's target is one complete learned graph and one model identity, separate from the deterministic `brain_stem/src/swarm_core/` execution/governance substrate and `brain_stem/training/stacey/` training support. The code in `brain_stem/models/stacey/core/` is currently only a shared-Core scaffold for understanding, reasoning, planning, consequence prediction, and internal-path selection; the complete graph constitution and internal learned paths are not implemented or trained. The product target is not eight separate layer models or a Core that routes to peer models.

The v0 shared-backbone architecture is explicitly a **configurable byte-level encoder-decoder Transformer experiment**, not a frozen final graph. `StaceyCoreConfig` currently configures only that scaffold's dimensions, layer counts, context bounds, and dropout; W0 must add the complete graph topology, internal paths, tensor ports, and residency contracts before production training. The UTF-8 byte codec has a stable 259-symbol vocabulary including PAD/BOS/EOS. Other graph architectures/tokenizers remain candidates to compare against the same complete-graph benchmark.

The graph receives one schema-validated `UnifiedContextIngress` with four matrices: raw language or structured event intent; the trusted four-field scope; a bounded canonical-state ledger snapshot with provenance; and measured resource/lease plus signed internal-graph-path availability and deterministic host-tool contracts. The deterministic host supplies and validates trusted scope and data permissions. Raw files, unbounded conversation logs, and arbitrary executable payloads are not model ingress.

For every turn, the shared graph emits one JSONL `CoreDecisionEnvelope` with four required primitives: (1) exact scope echo, checked against trusted ingress; (2) a task DAG naming internal graph paths and deterministic host tools with conditional edges; (3) per-step resource estimates, advisory until checked by deterministic admission; and (4) a calibrated `confidence_coefficient` plus structured clarification reason codes. It also carries transaction/correlation IDs and an internal predicted-consequence summary. The model does not output user-facing copy, executable code, shell commands, or file mutations. Invalid JSON, scope drift, unavailable paths, missing estimates, cyclic graphs, or execution while clarification is required are rejected.

`initialize_stacey_core` currently creates reproducible random weights for the shared-backbone scaffold from an explicit seed. Its parameter/raw-storage report excludes the unimplemented graph paths and is not a complete-model profile or runtime-memory measurement. `forward` returns token logits; bounded decoding produces tokens only. JSON parsing and semantic validation are deterministic operations. A confidence gate blocks internal-path and host-tool execution below threshold unless clarification was requested. Checkpoints use atomic replacement, explicit permissions, SHA-256 verification, and PyTorch's weights-only loader. Resume state binds optimizer/model/RNG/data cursor to the exact plan, dataset, trainer config, and best-checkpoint digest; it is not approval to activate a graph revision.

`brain_stem/models/stacey/core/inference.py` supplies a one-ingress adapter for the current scaffold: it encodes the four-matrix ingress, invokes bounded token generation, decodes one JSONL record, validates the envelope, and enforces a caller-injected confidence threshold. It returns a proposal only; it does not execute graph paths, reserve resources, or authorize actions. Its candidate ID/digest must be bound by a future single-graph lifecycle, not a per-capability model catalog.

`brain_stem/training/stacey/` is intentionally separate. Its teacher-forcing objective, strict corpus loader, and scratch SFT runner are separate from the model package. Tests use temporary synthetic fixture input/targets to prove finite loss/gradients, bounded optimizer updates, exact-plan optimizer/data-cursor resume, readiness denial, and checkpoint integrity; they consume no approved production dataset and do not train a useful Stacey model. No BPE tokenizer trainer, broad next-token pretraining, trusted production approval service, or trained weights are included.

**Current implementation state:** `brain_stem/models/stacey/core/` contains only a configurable, randomly initialized byte-level shared-backbone candidate and typed ingress/task-graph contracts. Synthetic smoke targets test tensor plumbing, finite loss/gradients, optimizer updates, seeding, bounded decoding, and checkpoint round trips; they do not establish learned capability. The complete Block 0–12 graph topology/weights/runtime do not exist. Confidence is untrained and uncalibrated; caller-supplied thresholds are temporary guards. The scaffold's parameter/storage estimates exclude unimplemented graph parts and do not measure runtime memory or accelerator residency.

Core parameter count and raw storage-size estimates are available to compare configuration candidates; neither estimates peak runtime memory, accelerator residency, speed, or trained quality. Do not present the sample small configuration or the under-400 MB goal as a chosen production architecture.

## 4. Contracts and Security Rules

`brain_stem/substrate/contracts.py` defines the in-process typed contracts. `brain_stem/schemas/contracts.schema.json` describes the serialized Phase 1 intent envelope. The current kernel accepts Python dataclasses directly; it does not yet decode JSON or invoke a runtime schema validator. Any serialized ingress adapter must validate against the schema and invoke the same scope checks before routing. The scope vector is exactly four fields; a missing, blank, extra, or mismatched field is rejected. Tenant isolation is based on trusted authorization context, not the scope payload alone.

### Rule I: Declarative Intent Only

Runtime actions are typed intent values, not shell arrays, executable strings, or arbitrary commands. Implemented signed actions include `ROUTE_TASK`, bounded `INSPECT_SYSTEM`, consent-bound `PROCESS_CONSENTED_AUDIO`, and `WRITE_WORKSPACE_FILE`; only the last reaches the separate operator-confirmed FB-038 prototype. Further create/modify/verify operations require explicit typed schemas and scope-specific authorization; no block writes directly to the filesystem. Source code intended for a future file edit may be opaque content data, never an instruction to execute it.

### Rule II: Twin-Receipt Mutation Guard

The Phase 1 routing slice performs no mutation, and Phase 3 remains an injected coordinator rather than a filesystem implementation. A separate workspace-scoped POSIX FB-038 prototype now stages/commits one file, compensates, reconciles conservatively, and requires an operator signature bound to intent, artifact, and release; a following projector records the committed result in FB-004. This is not a production cross-platform writer or trusted OS identity service. The mandatory order remains: validate and authorize; durably persist FB-027 `PREPARED`; stage/verify through FB-038; commit; verify final state; persist `OUTCOME`. On failure, compensate from recorded prior state; report `INDETERMINATE` if compensation cannot be verified; if `PREPARED` persistence fails, do not mutate.

### Rule III: No Hidden Hardcoding; Model and Provider Neutrality

Do not embed machine-specific budgets, memory cushions, model sizes, filesystem locations, provider endpoints, hardware flags, test fault switches, or mutable policy values in the kernel or block logic. Supply operational values through validated typed configuration or an injected capability/resource adapter; fail clearly when required configuration is absent rather than silently selecting a machine-specific default. Resolve resource budgets from a named runtime profile and current resource snapshot, with the profile stored/configured outside the core.

Stable protocol invariants are not hidden configuration: block IDs, the four scope field names, typed action names, schema version, and receipt state names remain explicit in contracts and code. Test fixtures may contain example values, but fault injection belongs in fake adapters, not untrusted intent payloads. The Phase 1 keyword vocabulary and `mock.general` route are temporary deterministic fixtures, not production classification or an extensible capability registry.

Core interfaces use functional capability keys and resource profiles, never commercial model names, provider URLs, fixed IP addresses, or cloud labels. Optional runtime and hardware adapters own their own configuration. The core does not depend on any model provider.

### Rule IV: Local-First In-Process Runtime

The kernel, blocks, worker, FB-027, and FB-038 boundaries are local in-process modules. Do not add always-running third-party daemons, unmanaged socket listeners, or mandatory external services. A future optional library dependency must not silently create an external runtime service.

### Additional System Laws

- **Taxonomy isolation:** exactly Block 0 plus Blocks 1–15; each block has one documented functional responsibility.
- **Critique coercion:** all future generated or worker-produced output passes Block 6, then Block 8, before the caller receives it.
- **Resource cleanup:** any future transient resource is released deterministically on success, failure, and cancellation, using structured cleanup (`finally`/context managers). Python garbage collection alone is not proof of OS unmapping or device-memory release.
- **Planning order:** Blocks 2 and 3 precede any future Block 12 language generation.
- **Consensus:** ambiguous or conflicting assertions must be resolved by a future validation-cluster consensus flow before committing to FB-004, the canonical ledger. Neither consensus nor FB-004 is implemented.
- **Provenance:** future ledger assertions must be source-linked through Block 14. No immutable hash chain is implemented today.
- **Scope-bound patches:** future mobile updates must bind to all four scope fields. Mobile distillation and autonomous splinter creation are deferred and require a separate security and lifecycle design in this master document before implementation.
- **Hardware tuning:** Block 15 may host optional capability detection and tuning. CUDA/RTX/AVX profiles are not core requirements and cannot be hardcoded into the portable kernel.

## 5. Failure Semantics

Malformed or incomplete intent, missing identifiers, unsupported action, incomplete trusted scope, or any four-field mismatch raises `IngressRejected` before worker execution. A structurally invalid plan or mismatched worker result raises `IntegrityViolation`; no execution report is returned. Worker exceptions propagate to the caller and do not become success. The Phase 1 prototype performs no persistent mutation. The Phase 3 coordinator connects receipts to injected workers and mutation authorities; real target mutation and compensation remain unimplemented.

### Phase 2: Lifecycle and Integrity

**Status: Local mutation/provenance prototypes and orchestration tests implemented; production authorities remain incomplete.** The coordinator still composes injected authorities; a separate signed-scope FB-038 workspace writer provides staged single-file commit, compensation, and conservative crash reconciliation, and a projector links successful writes into reviewed FB-004 state. #### No-Hardcoding Resource Admission

- Inject a validated `ResourcePolicy` and a live `ResourceSnapshot` from the selected runtime adapter. Represent capacities in one explicit base unit (bytes) and identify the resource domain (for example host memory, mapped-file residency, or device memory). Do not put `6144`, `1536`, or `350` MB defaults in the kernel.
- A 6 GB device limit or 1.5 GB PagedAttention cushion is an optional named profile value only when the selected backend actually exposes that resource and cache. It is not a platform-wide invariant. Missing or stale measurements fail closed for the operation that needs them; they do not fall back to a guessed ceiling.
- Admission reserves the requested budget atomically before work. Use a per-process synchronized lease/allocator so concurrent tasks cannot all pass against the same free capacity. Validate configured and requested values as finite, non-negative, and within representable limits. Releasing the lease in structured cleanup is authoritative; `gc.collect()` is not a memory-release guarantee and must not be used as a substitute for admission accounting.
- Inject fake resource providers and explicit budgets in tests. Assert exact boundary behavior, over-budget denial before worker invocation, concurrent reservation safety, and release on every exit path.

#### Two-Phase Receipts and Mutation Order

Keep FB-027 and FB-038 as local in-process authority interfaces. Their storage path, durability mode, and mutation target authorization come from explicit configuration and trusted scope, not hard-coded paths. JSONL may be a serialization choice, but does not imply a server or listener.

For a mutating intent, the order is:

1. Validate the typed intent, all four trusted scope fields, transaction identity/idempotency, and target authorization.
2. Acquire the resource lease. Pure validation and admission do not modify the target.
3. Persist and durably flush an immutable FB-027 `PREPARED` event containing enough transaction, scope, target, and prior-state/delta references to recover. If it cannot be persisted, deny before any worker side effect or target mutation.
4. Execute through the capability worker and FB-038 staging boundary; never write the target directly from a block. Run Block 6, then Block 8, and verify the staged result before commit.
5. FB-038 commits the authorized change. FB-027 appends a durable `OUTCOME` event only after verifying the committed state.
6. If any step after `PREPARED` fails, FB-038 compensates from recorded prior state/delta and verifies restoration. Append an immutable compensation outcome when possible. If restoration cannot be verified, return `INDETERMINATE`, never success, and block further mutations against the unresolved transaction/target until reconciliation.
7. Release the resource lease in `finally` on success, failure, or cancellation. No telemetry path may translate `INDETERMINATE` into success.

Receipts are append-only state transitions, not mutable status dictionaries: `PREPARED` -> `OUTCOME`, `COMPENSATED`, or `INDETERMINATE`. Enforce transaction uniqueness/idempotency and serialized state transitions within the process. A crash that leaves only `PREPARED` is unresolved, not success; recovery must inspect the durable journal and target state and compensate or reconcile before permitting a retry. If writing the terminal receipt itself fails, preserve the unresolved prepared state and surface an explicit failure; do not fabricate a durable terminal record.

#### Phase 2 Test Matrix

Keep the four proposed scenarios: admission overflow is denied; worker failure is compensated; outcome persistence failure plus failed compensation returns `INDETERMINATE`; resource accounting returns to baseline in all paths. Improve them as follows:

- Inject faults using fake receipt-store, worker, resource-provider, and mutation-authority implementations. Never accept `test_inject_fault` or a magic target path from an intent.
- Add PREPARED persistence failure (assert worker and mutation authority were never called), successful commit and durable OUTCOME, failed compensation with no success result, idempotent duplicate transaction handling, malformed/stale resource snapshots, concurrent admission, cleanup after cancellation/exception, and startup recovery of unresolved PREPARED events.
- Use a temporary isolated store and test targets supplied by fixtures. No machine-specific paths, hardware ceilings, target files, or provider labels live in production code.

The transaction ordering and acceptance tests are required before enabling file mutation; they do not prevent progress on independent CPU-only work. Keep Phase 2 local and in-process, with no daemon or socket service. A resource domain that the selected CPU mock runtime cannot observe is not claimed as protected by its test results.

### Phase 3: Transaction Coordinator

Add a synchronous in-process coordinator that composes the Phase 2 lease manager and receipt ledger with injected stage worker, ordered Block 6/8 verifier, and FB-038 commit/compensation authority. Validate and authorize before admission; reserve a lease; persist `PREPARED`; stage and verify; commit; append `OUTCOME`. A failure before commit invokes compensation. Verified compensation records `COMPENSATED`; failed compensation raises an explicit `INDETERMINATE` error. If commit was attempted but terminal `OUTCOME` persistence fails, do not compensate based on an uncertain receipt write; surface unresolved state and require journal/target reconciliation. No path returns success for unresolved or indeterminate work. Duplicate completed requests are idempotent; unresolved `PREPARED` transactions block replay pending reconciliation. Resource leases release on all exits.
