## 1. Purpose and Operating Model

**Stacey is one model identity and one installable model bundle:** a learned Core plus its internal, dynamically activated capability weights, shared scoped world state, and the deterministic execution machinery that keeps the model coherent and safe. It is not a multi-model operating system or an OS router. The Core is the stable cognitive identity; it interprets context, reasons about system/task state and action consequences, checks whether the bundle has the capabilities and controls a task needs, compiles or revises task graphs, selects internal capability IDs, and integrates specialist results. Internal weights are loaded only when needed; the complete bundle need not be resident in GPU memory, and the Core itself may be placed according to measured host/accelerator capacity. The Core does not generate conversational copy or directly perform every task.

The Core is neural cognition; deterministic controls are the embedded execution and safety substrate of the Stacey bundle, not a separate user-facing OS. The substrate enforces authorization, resource admission, internal weight lifecycle, typed contracts, receipts, and action policy. The Canonical World Model Ledger (FB-004) is provenance-bearing persistent state that the Core can query and update; it is not the Core's weights or hidden activations. Model proposals do not become trusted world state until validated and committed through deterministic controls.

### Model Identity and Adaptive Cognition

Stacey analyzes the capability/control needs of a task as part of its own reasoning. Its typed `SystemInspectionDirective` names the purpose, exact probe IDs, required internal capability IDs, required controls, and minimum resources; it must be paired with clarification and an empty runnable task graph. The runtime converts it into a pending consent request and dispatches no specialist. Only after an operator grants a separate exact-digest `INSPECT_SYSTEM` signature may bounded adapters observe the allowlisted host surfaces. The Core receives a typed capability/control inventory, not ambient credentials or unrestricted system access. The current prototype reports system fit, but host orchestration must still carry reviewed evidence into a newly authorized Core ingress before continuing the task. The Core decides which internal capability IDs are relevant; when sight, audio, coding, temporal analysis, or memory retrieval is unnecessary, those weights remain unloaded or their path is not invoked.

Self-expansion is an internal model-building capability, not autonomous authority. The prototype `SystemInspectionService` can, after a signed `INSPECT_SYSTEM` grant, compare explicitly requested probes and capability/control needs against typed evidence and the exact active signed bundle; it reports missing capabilities, controls, or measured resources and performs no host writes or weight loads. Stacey may use approved data and observed, provenance-bearing outcomes to propose new internal specialist weights, adapters, or system-fit bundle revisions, then train/assemble and evaluate those candidates within explicit budgets. A candidate becomes part of the active Stacey bundle only after independent rights, safety, capability, compatibility, and release approval. Promotion is atomic and rollbackable; an unapproved or failed candidate cannot alter the active model. Third-party weights remain separately license-bound even when packaged inside Stacey's single deployable bundle. No specialist or Core output can grant itself host permissions, sign approvals, or activate its own release.

The design is provider-neutral. Model runtimes, hardware backends, identity sources, and future surface connectors are replaceable adapters, not hard-coded core dependencies. Local laptop, mobile edge, and optional private-cloud execution all belong in the design; local hardware is the first evaluation surface. Cross-surface placement depends on capability fit, measured resources, privacy scope, availability, and latency/cost policy. It is not a fixed model-to-device map.

The current repository is not a trained learned swarm: it contains a signed-ingress single-model runtime with pinned Core/artifact leases and dynamic specialist dispatch; deterministic workspace actions and provenance projection; bounded visual, audio, structured-data, temporal, relational, volatility, and response services; a review-only scratch-Core Foundry; and plan-bound optimizer/data-cursor resume. These are tested prototypes using fixture authorities/backends. There are no trained Core/specialist weights, rights-cleared real corpus, protected human-reviewed holdout, broad pretraining backend, production key provisioning/revocation, production approval services, qualified Android NPU adapter, or private-cloud runtime.

The system is intended to expand across reasoning/planning, coding, document and data work, multimodal interaction, communication, and authorized actions. "Everything imaginable" is an extensibility goal, not a guarantee that any finite model set solves every task. Each capability claim must be demonstrated by task-specific evaluation.

## 2. Taxonomy and Implementation Status

There is one persistent learned World Model Core (Block 0) and an initial set of fifteen transient capability slots (Blocks 1–15). Stacey is the collective across the Core and specialist models. The 8 cognitive layers describe the overall flow; the 15 blocks refine capability roles. Neither count dictates model-file count. The starter taxonomy is extensible by append-only, versioned capability IDs. A capability may have multiple candidate artifacts, and a model may serve multiple capabilities only when evaluation justifies it. Current specialist implementations are software mocks; Stacey Core v0 is randomly initialized and untrained. The supplied sizes and hot-swap performance claims remain unverified targets.

### Eight Cognitive Layers

These are functional stages, not a requirement to train exactly eight models:

1. **Sense:** learned perception models turn image, audio, and other modality input into structured observations.
2. **Understand:** the Core interprets raw user intent by default; a separate understanding specialist is optional if evaluation shows it helps.
3. **Reason:** the Core builds hypotheses, handles ambiguity, predicts consequences, and creates/revises dependency-aware plans.
4. **Act:** learned specialists propose typed operations; deterministic services authorize, stage, commit, and receipt them.
5. **Specialist network:** expandable learned capability slots handle coding, extraction, critique, language, and future domains.
6. **Memory:** deterministic scoped stores preserve facts, episodes, artifacts, and provenance; learned retrieval/ranking may assist but cannot silently rewrite canonical state.
7. **Orchestration:** the Core chooses the cognitive path; deterministic scheduling enforces resource budgets, isolation, and model lifecycle.
8. **Execution tools:** deterministic permissioned interfaces act on the local or explicitly authorized external environment.

#### Build Order to Charter-Complete Stacey

1. **Freeze the charter-derived capability contract:** Blocks 0–15 and Surfaces A/B/C are the plan scope; enumerate the accepted task, modality, file-format, action, identity, privacy/retention, and resource envelopes for each block/surface in versioned contracts. Block 15 remains explicitly optional and must have a measured include/defer decision. Convert each charter requirement to an acceptance case before selecting production models.
2. **Complete the deterministic perimeter:** trusted authorization, real measured resource providers, canonical world-state ledger, real staged local mutation/compensation for v1 tools, crash recovery, sandbox, and model lifecycle. Keep learned outputs non-authoritative.
3. **Complete the training/evaluation inputs:** owner-provided training hardware profile, approved rights-cleared corpus, trusted human review/approval, protected holdout storage, and leakage/contamination checks. Finalize the model/tokenizer/config and train/evaluation manifests against those inputs.
4. **Train the Core candidate:** perform rights-cleared scratch pretraining for any broad language/code capability claim, then train the narrow task-graph behavior. If broad pretraining data or compute is unavailable, the release must be explicitly restricted to the measured task scope and cannot claim general-purpose language competence. Evaluate on the protected holdout and calibrate thresholds; do not promote the current random scaffold based on plumbing tests.
5. **Integrate and harden the first learned path:** run Core inference, strict parse, scope/capability/DAG/confidence validation, live admission, specialist execution, result verification, receipt, and recovery through real local adapters.
6. **Expand by evidence:** build and qualify specialist artifacts for measured failure clusters, one capability at a time. Add vision/audio/retrieval/mobile/cloud only with independent specs, provenance, and acceptance gates.
7. **Surface A release:** qualify the full required local capability set, tools, runtime lifecycle, recovery, package and protected evaluation on a named laptop/host profile. Surface A is not whole-system completion.
8. **Surface B mobile edge:** implement a device-specific runtime/processor adapter, compact scratch-trained compatible artifacts, authenticated/scope-bound updates, lease/power management, offline behavior, privacy controls, and rollback; test on named supported devices and NPUs.
9. **Surface C private cloud:** implement a separately authenticated private deployment of approved Stacey artifacts, encrypted/minimized context transfer, explicit user/tenant authorization, network failure/cancellation, local result validation, receipts, and deletion/retention controls. Cryptographic secrets remain in host security components; they are never passed to model input.
10. **Governed Foundry:** implement candidate generation/training orchestration as a bounded, auditable job system that can build and evaluate candidates from approved data, bind every artifact to source/config/run digests, and submit passing candidates for human approval. It may not self-approve, self-deploy, silently import outside weights, or alter the active collective.
11. **Full charter release gate:** all mandatory Blocks 0–14 have implemented capability paths (learned or explicitly designed deterministic services per their contracts); Block 15 is implemented or formally deferred with evidence; Core and required specialists pass protected per-artifact and end-to-end collective suites; A/B/C deployments pass security, privacy, failure/recovery, resource, and rollback gates; and Foundry outputs remain review-gated. Beyond-charter capabilities require new versioned scope and tests.

### Composite Stacey Collective: Model Parts and Lifecycle

The deliverable is **one installable, versioned Stacey model bundle with one model identity**. Its internal weights may be modular and dynamically resident, but users install and invoke Stacey as one model; the deterministic lifecycle/safety machinery is part of that model package, not an OS router or a competing agent. The bundle binds its Core weights, approved internal specialist weights/adapters, shared scoped state interfaces, capability contracts, deterministic safety substrate, and release manifest. The Core owns understanding/reasoning/planning/selection and decides which internal capability IDs to engage. Some capabilities may remain deterministic services when learning adds no measured value.

#### Release and Artifact Manifests

Every cohesive deployment is identified by a `StaceyCollectiveReleaseManifest` containing:

- Collective ID/version, manifest digest, release approval, and rollback target.
- Exact Core artifact digest, architecture/config digest, tokenizer digest, backend/runtime compatibility, training/data lineage, evaluation/calibration evidence, and resource profile.
- A capability-to-artifact mapping for required specialists; each mapping binds exact artifact digest/version, capability contract/schema version, architecture, tokenizer or modality processor, runtime backend, dependency set, training lineage, rights review, evaluation evidence, and approval reference.
- An explicit artifact kind: `FULL_MODEL`, `LORA_ADAPTER`, `TOKENIZER_OR_PROCESSOR`, or `DETERMINISTIC_COMPONENT`. A LoRA/adapter must bind to the exact base artifact digest, architecture/config, target module names/shapes, tokenizer/vocabulary, adapter format/rank, and runtime support. It is invalid against any other base unless separately evaluated and registered. An independent specialist checkpoint declares its own architecture, tokenizer/processor and backend; it is not a drop-in weight sheet for Block 0.
- Placement and lifecycle policy: persistent-Core requirements, specialist transient/resident policy, concurrency limits, permitted resource domains, measured load profile, maximum context/batch, and eviction rules.
- Software bill of materials and exact runtime/library versions. No arbitrary filesystem scan or ambient model discovery is allowed.

The candidate catalog is currently in-memory metadata only. It must become a durable, integrity-checked registry that resolves a capability to one or more approved candidates without silently selecting an unapproved artifact. The Core plan names capabilities and blocks, not brands or artifact paths. Deterministic selection uses capability/schema compatibility, approval state, measured resources, placement/privacy scope, availability, latency/cost policy, and evaluation status.

#### Runtime Interfaces

The code-completion target has four explicit seams:

1. `CapabilityContract`: versioned typed request/response schemas independent of model tokenizers. A model-specific adapter encodes requests and decodes outputs; results pass the same host validators regardless of backend.
2. `ModelRuntimeBackend`: provider-neutral inspect/verify/load/infer/unload operations for a manifest-approved artifact. Backend-specific libraries and processor/tokenizer assets stay behind the adapter.
3. `ModelLifecycleManager`: resolves approved artifact references, obtains resource leases, manages resident handles and concurrent users, and unloads or quarantines artifacts.
4. `CollectiveScheduler`: executes the validated DAG, requests capabilities from the lifecycle manager, orders conditional steps, routes outputs through Block 6 then Block 8, records receipts, and releases handles/leases on every exit path.

The prototype connects signed ingress authorization, the Core inference adapter, conditional scheduler, active-release lifecycle, and typed fixture backends. Contract version/schema digest and each step's resource estimate are checked against the signed release/artifact before loading. This is not a production collective path: there are no trained weights or production model backends, and the scheduler is not yet connected to FB-038 action execution, FB-004 admission, or release-level workflow receipts/telemetry.

#### Load/Use/Unload State Machine

`REGISTERED -> APPROVED -> UNLOADED -> LOADING -> RESIDENT -> IN_USE -> RESIDENT -> EVICTING -> UNLOADED`. Failures transition to `FAILED` or `QUARANTINED`; approval and integrity failures never enter `LOADING`. `RESIDENT` means verified artifact is mapped and accounted for; `IN_USE` is protected by one or more task leases. Concurrent calls may share a compatible read-only handle only when the backend declares that safe.

#### Dynamic Weight Pool and Adapter Switching

The self-trained Stacey Core is the stable model identity and cognitive control; new internal weights become a supported system-fit bundle candidate only when their capability and joint workflow pass evaluation. The Core does not silently rewrite or self-promote its active weights. A system-fit candidate records the exact Core, capability artifacts, adapters, modality processors, resource profile, and allowed host integrations selected for an operator-authorized system scope. Missing capabilities may trigger a bounded Foundry build request from approved data or approved license-bound specialists; they do not authorize arbitrary imports or on-the-fly tensor mixing. The registry supports two distinct internal extension paths: (a) a `LORA_ADAPTER` applied to its exact compatible Stacey base for learned specialization, and (b) a separately loaded `FULL_MODEL` capability component with its own architecture/tokenizer/processor/backend. Adapters share a tokenizer only when the bound base/vocabulary contract requires and supports it; shared tokenization is not a correctness guarantee. A tokenizer/vocabulary change requires compatible embedding/output weights and a separately versioned base, not just a LoRA file.

Keep the Core resident only when its measured host/device profile supports that choice; no full-brain or all-specialists-on-GPU assumption is allowed. Internal capability weights may be warm-resident, pre-staged in host memory, mapped/offloaded, or loaded on demand according to the selected backend. If the Core itself must move or unload, the bundle must preserve a stable request/control context and recover at a task boundary. Reserve staging capacity in **bytes** for the incoming artifact plus backend-specific temporary allocations; do not hard-code a count such as "five resident models plus one slot." Multiple weights may share capacity only if the backend supports concurrent handles/adapter activation and resource accounting proves the peak fits. A same-base adapter switch, full-model load, or CPU-to-GPU transfer has different latency and memory costs and must be measured separately.

When capacity is insufficient, the scheduler picks only an approved compatible artifact, loads/verifies it in staging without overwriting any active tensors, waits for safe completion at a task boundary, atomically updates the runtime binding, and evicts only an artifact with no active lease. Eviction priority is a deterministic policy over task priority, active leases, measured memory, and configured latency/cost—not a choice the Core implements as memory manipulation. If loading, switching, or confirmed release fails, retain the old valid binding when safe, release only confirmed resources, quarantine uncertain slots, and return a structured unavailable/resource failure or clarification. Every transition is receipt/telemetry-bound to artifact digest, task, backend, measured allocation, and outcome. This policy supports a large on-disk library without promising that all weights fit in GPU memory or that swapping is instantaneous.

The performance/quality evaluation must compare at least: Core-only, Core plus a compatible adapter, and Core plus a separately loaded specialist for relevant tasks. Record cold-load, warm activation, adapter application, inference, eviction/release latency, peak host/device memory including staging/activations/KV/workspaces, task quality, failure/rollback behavior, and concurrent-load interference. Remove or disable any weight option that fails its capability, safety, provenance, licensing, or resource gate.

- **Before load:** verify release-manifest signature/digest, artifact digest, dependency and backend compatibility, license/provenance approval, capability contract, and resource estimate; then reserve the measured lease before allocating device state.
- **During use:** bind every call to transaction/correlation ID, scope, candidate digest, and capability contract. Enforce isolation, timeout/cancellation policy, context/batch limits, and output validation. No inference result skips authorization or Block 6/8 checks.
- **Before eviction:** stop new leases, wait for or cancel active calls under explicit policy, release the backend handle, and confirm resource accounting returned to the measured state. Never evict an in-use model.
- **On failure:** release only resources proven released. If unload/memory accounting is uncertain, quarantine the artifact/device slot and deny further admission there until reconciliation; do not claim successful cleanup.
- **Rollback/update:** stage and verify a new artifact/release manifest before activation. Switch atomically at a task boundary, preserve the prior approved release for rollback, and reject mixed incompatible contract versions.

The Core may remain resident only while the verified target profile can sustain it. Specialists are loaded just in time and evicted by policy when idle and needed memory is reclaimed. No latency or hot-swap guarantee is accepted until measured on each supported backend. CUDA, CPU mapping, mobile NPU, and private-cloud backends may have different lifecycle semantics and require separate integration tests.

### Charter-Complete Collective Gate

**Code-complete** for the frozen charter means the implementation and training pipelines for every Block 0–15 capability, the collective manifest/registry/runtime, the required deterministic authorities, and Surface A/B/C deployment adapters pass integration, failure, and security tests. ### Stacey Core v0 Contract

Stacey Core v0 is **one learned model** handling understanding, reasoning, planning, consequence prediction, and specialist selection. These are unified responsibilities inside one Core candidate, not separate learned models on every ingress. Specialist capabilities remain separate slots activated by the Core's plan.

The Core receives one schema-validated Unified Context Ingress Envelope containing exactly four data matrices:

1. **Inbound intent vector:** raw user language or a typed upstream event signal. The Core must not receive raw file dumps or unbounded system logs; those are summarized and sourced into ledger assertions by the host/specialists.
2. **Trusted scope lock:** tenant, user, project, and workspace IDs supplied by the deterministic host. The Core must echo them exactly; it cannot authenticate or change them.
3. **Canonical ledger snapshot:** bounded state assertions, verified facts, current environment state, and provenance references already filtered to the trusted scope.
4. **Hardware and swarm capability matrix:** timestamped resource-domain measurements, active leases, and registered/approved specialist slots with capability IDs, status, artifact digest, modalities, and estimated requirements.

Before any specialist or tool runs, the Core emits one JSONL Declarative Task Graph Envelope. Required contents:

- Transaction and correlation IDs, `assigned_block_id=BLOCK_0_CORE`, and an internal predicted-consequences summary.
- The unchanged trusted four-field scope vector.
- An acyclic task DAG naming registered capability slots, target block IDs, conditional dependencies, and exactly one per-step resource estimate. Estimates are untrusted predictions; the deterministic lease manager checks fresh measurements and may deny the plan.
- A calibrated `confidence_coefficient` in `[0,1]`, where higher means more confident, plus structured clarification reason codes. The host compares it against an injected minimum-confidence policy; below threshold, it refuses specialist dispatch unless the output explicitly requests clarification. Calibration is an empirical property, not guaranteed by emitting a number.

The Core output is not user-facing chat, executable code, shell commands, or a direct mutation. Clarification is an action directive with reason codes; a separate Respond capability may phrase it for the user. Before execution, a deterministic validator checks transaction identity, exact scope echo, registered and available capability/block pairs, DAG acyclicity, resource-estimate coverage, and the clarification threshold. Resource estimates do not grant or reserve memory.

## 3. Building Blocks and Control Flow

The `brain_stem/substrate/` package is the Phase 1 composition root and typed contract boundary. `SubstrateKernel` is the light kernel; each implemented block has its own directory under `brain_stem/substrate/blocks/`. The mock worker is separately isolated under `brain_stem/substrate/workers/`. The Phase 2–4 building blocks live under `brain_stem/src/swarm_core/`. Tests exercise them without a server, model download, GPU, or external process.

For `ROUTE_TASK`, the current control flow is:

1. Ingress accepts a typed `Intent` and trusted `authorized_scope`.
2. The kernel requires non-empty `tenant_id`, `user_id`, `project_id`, and `workspace_id` on both scopes and requires exact equality. It also checks the supported action and non-empty transaction ID, correlation ID, and goal. Reject before invoking any worker on failure.
3. Block 2 classifies the intent; Block 3 creates a task plan.
4. The registered in-process CPU mock worker executes the plan.
5. Block 6 validates step uniqueness, the registered mock capability, status, transaction/correlation IDs, and completed steps.
6. Block 8 verifies the plan transaction and returned goal against the original intent.
7. Only after both checks pass does the kernel return an `ExecutionReport` to its in-process caller.

Block 6 always precedes Block 8. There is no network port or output listener. The host invoking the kernel is responsible for obtaining `authorized_scope` from a trusted local identity boundary; comparing two untrusted caller-supplied values is not authorization. The current prototype accepts that trusted scope as an explicit method argument and does not implement identity authentication or a ledger.

The current classifier and decomposer are deliberately small deterministic mocks, not trained models. The current planner emits one `mock.general` step. Unknown capabilities fail closed in Block 6. The worker interface is replaceable without changing the ingress, contract, or validation boundaries.

## 3A. Stacey Core v0 Skeleton

Stacey is the total learned Core-plus-specialist collective. The Core in `brain_stem/models/stacey/core/` is separate from the deterministic `brain_stem/src/swarm_core/` execution and governance substrate and from the separate `brain_stem/training/stacey/` training support. It is one learned model candidate for understanding, reasoning, planning, consequence prediction, and specialist selection; it is not eight separate layer models and is not the complete Stacey collective by itself.

The v0 architecture is explicitly a **configurable byte-level encoder-decoder Transformer experiment**, not a frozen final architecture. `StaceyCoreConfig` injects dimensions, layer counts, context bounds, and dropout. The UTF-8 byte codec has a stable 259-symbol vocabulary including PAD/BOS/EOS, avoiding dependence on an existing installed model or tokenizer. Other architectures/tokenizers remain candidates to compare using the Core benchmark.

The neural model receives one schema-validated `UnifiedContextIngress` with four matrices: raw language or structured event intent; the trusted four-field scope; a bounded canonical-state ledger snapshot with provenance; and measured resource/lease plus approved-specialist capability metadata. The deterministic host supplies and validates trusted scope and data permissions. Raw files, unbounded conversation logs, and arbitrary executable payloads are not model ingress.

For every turn, Stacey Core v0 is intended to emit one JSONL `CoreDecisionEnvelope` with four required primitives: (1) exact scope echo, checked against trusted ingress; (2) a task DAG naming capability slots and conditional edges; (3) per-step resource estimates, advisory until checked by deterministic lease/admission control; and (4) a calibrated `confidence_coefficient` plus structured clarification reason codes. It also carries transaction/correlation IDs and an internal predicted-consequence summary. The Core does not output user-facing conversational copy, executable code, shell commands, or file mutations. Invalid JSON, scope drift, unavailable capability selection, missing resource estimates, cyclic graphs, or a plan that dispatches while clarification is required are rejected before execution.

`initialize_stacey_core` creates reproducible random initial weights only from an explicit seed. The configurable candidate reports parameter count and a raw weight-storage estimate for profile comparisons; neither is a runtime-memory measurement. `forward` returns token logits; greedy decoding is bounded by injected config and produces tokens only. JSON parsing and semantic envelope validation are separate, deterministic operations. A deterministic confidence-policy gate blocks specialist dispatch below a caller-injected threshold unless clarification was requested. Model checkpoints use atomic replacement, an explicit permission mode, SHA-256 verification, and PyTorch's weights-only loader. A separate resume checkpoint binds optimizer/model/RNG/data cursor to the exact plan, dataset, trainer config, and best-model digest; it is not itself an inference artifact or candidate approval.

`brain_stem/models/stacey/core/inference.py` supplies a one-ingress inference adapter: it encodes the four-matrix ingress, invokes bounded token generation, decodes one JSONL record, applies the strict envelope validator, and enforces a caller-injected confidence threshold. It returns a validated decision only; it does not dispatch specialists, reserve resources, or authorize actions. Its candidate ID and artifact digest are supplied by the caller and must be bound to the verified loaded checkpoint by the hosting candidate lifecycle.

`brain_stem/training/stacey/` is intentionally separate. Its teacher-forcing objective, strict corpus loader, and scratch SFT runner are separate from the model package. Tests use temporary synthetic fixture input/targets to prove finite loss/gradients, bounded optimizer updates, exact-plan optimizer/data-cursor resume, readiness denial, and checkpoint integrity; they consume no approved production dataset and do not train a useful Stacey model. No BPE tokenizer trainer, broad next-token pretraining, trusted production approval service, or trained weights are included.

**Stacey Core v0 implementation state:** `brain_stem/models/stacey/core/` contains a configurable, randomly initialized byte-level encoder-decoder candidate and typed four-matrix ingress/task-graph output contracts. The current smoke path uses synthetic fixture targets to check tensor shapes, finite forward/loss values, gradients, parameter updates, deterministic seeding, bounded decoding, and SHA-256 checkpoint round trips. It does not establish that random weights understand intent, reason, predict outcomes, or produce valid plans reliably. The `confidence_coefficient` uses higher values for greater confidence; its calibration is untrained and unmeasured. The runtime's caller-supplied threshold is the safeguard until learned calibration is evaluated. Parameter count and raw weight-storage estimates are exposed for profile comparison, but neither measures runtime memory or accelerator residency.

Core parameter count and raw storage-size estimates are available to compare configuration candidates; neither estimates peak runtime memory, accelerator residency, speed, or trained quality. Do not present the sample small configuration or the under-400 MB goal as a chosen production architecture.

## 4. Contracts and Security Rules

`brain_stem/substrate/contracts.py` defines the in-process typed contracts. `brain_stem/schemas/contracts.schema.json` describes the serialized Phase 1 intent envelope. The current kernel accepts Python dataclasses directly; it does not yet decode JSON or invoke a runtime schema validator. Any serialized ingress adapter must validate against the schema and invoke the same scope checks before routing. The scope vector is exactly four fields; a missing, blank, extra, or mismatched field is rejected. Tenant isolation is based on trusted authorization context, not the scope payload alone.

### Rule I: Declarative Intent Only

Runtime actions are typed intent values, not shell arrays, executable strings, or arbitrary commands. Implemented signed actions include `ROUTE_TASK`, bounded `INSPECT_SYSTEM`, consent-bound `PROCESS_CONSENTED_AUDIO`, and `WRITE_WORKSPACE_FILE`; only the last reaches the separate operator-confirmed FB-038 prototype. Further create/modify/verify operations require explicit typed schemas and scope-specific authorization; no block writes directly to the filesystem. Source code intended for a future file edit may be opaque content data, never an instruction to execute it.

### Rule II: Twin-Receipt Mutation Guard

The Phase 1 routing slice performs no mutation, and Phase 3 remains an injected coordinator rather than a filesystem implementation. A separate workspace-scoped POSIX FB-038 prototype now stages/commits one file, compensates, reconciles conservatively, and requires an operator signature bound to intent, artifact, and release; a following projector records the committed result in FB-004. This is not a production cross-platform writer or trusted OS identity service. The mandatory order remains: validate and authorize; durably persist FB-027 `PREPARED`; stage/verify through FB-038; commit; verify final state; persist `OUTCOME`. On failure, compensate from recorded prior state; report `INDETERMINATE` if compensation cannot be verified; if `PREPARED` persistence fails, do not mutate.

### Rule III: No Hidden Hardcoding; Model and Provider Neutrality

Do not embed machine-specific budgets, memory cushions, model sizes, filesystem locations, provider endpoints, hardware flags, test fault switches, or mutable policy values in the kernel or block logic. Supply operational values through validated typed configuration or an injected capability/resource adapter; fail clearly when required configuration is absent rather than silently selecting a machine-specific default. Resolve resource budgets from a named runtime profile and current resource snapshot, with the profile stored/configured outside the core.

Stable protocol invariants are not hidden configuration: block IDs, the four scope field names, typed action names, schema version, and receipt state names remain explicit in contracts and code. Test fixtures may contain example values, but fault injection belongs in fake adapters, not untrusted intent payloads. The Phase 1 keyword vocabulary and `mock.general` route are temporary deterministic fixtures, not production classification or an extensible capability registry.

Core interfaces use functional capability keys and resource profiles, never commercial model names, provider URLs, fixed IP addresses, or cloud labels. Optional runtime and hardware adapters own their own configuration. The core does not depend on any model provider.

### Rule IV: Local-First In-Process Runtime

The kernel, blocks, worker, FB-027, and FB-038 boundaries are local in-process modules. Do not add always-running third-party daemons, unmanaged socket listeners, or mandatory external services. A future optional library dependency must not silently create an external runtime service.

### Additional System Laws

- **Taxonomy isolation:** exactly Block 0 plus Blocks 1–15; each block has one documented functional responsibility.
- **Critique coercion:** all future generated or worker-produced output passes Block 6, then Block 8, before the caller receives it.
- **Resource cleanup:** any future transient resource is released deterministically on success, failure, and cancellation, using structured cleanup (`finally`/context managers). Python garbage collection alone is not proof of OS unmapping or device-memory release.
- **Planning order:** Blocks 2 and 3 precede any future Block 12 language generation.
- **Consensus:** ambiguous or conflicting assertions must be resolved by a future validation-cluster consensus flow before committing to FB-004, the canonical ledger. Neither consensus nor FB-004 is implemented.
- **Provenance:** future ledger assertions must be source-linked through Block 14. No immutable hash chain is implemented today.
- **Scope-bound patches:** future mobile updates must bind to all four scope fields. Mobile distillation and autonomous splinter creation are deferred and require a separate security and lifecycle design in this master document before implementation.
- **Hardware tuning:** Block 15 may host optional capability detection and tuning. CUDA/RTX/AVX profiles are not core requirements and cannot be hardcoded into the portable kernel.

## 5. Failure Semantics

Malformed or incomplete intent, missing identifiers, unsupported action, incomplete trusted scope, or any four-field mismatch raises `IngressRejected` before worker execution. A structurally invalid plan or mismatched worker result raises `IntegrityViolation`; no execution report is returned. Worker exceptions propagate to the caller and do not become success. The Phase 1 prototype performs no persistent mutation. The Phase 3 coordinator connects receipts to injected workers and mutation authorities; real target mutation and compensation remain unimplemented.

The phases below are maintained only here. A phase is implementation sequencing, not a gate that blocks independent work. Record outcomes inline in Section 7 and keep moving when an unmet item is safely deferrable.

### Phase 0: Architecture and Contract Baseline

### Phase 1: CPU-Only General Routing

**Status: Implemented and tested.** Keep the router in-process; use deterministic mock workers. Require exact four-field scope checks, planning before work, and ordered Block 6 then Block 8 validation. Run with the Python standard library only.

### Phase 2: Lifecycle and Integrity

**Status: Local mutation/provenance prototypes and orchestration tests implemented; production authorities remain incomplete.** The coordinator still composes injected authorities; a separate signed-scope FB-038 workspace writer provides staged single-file commit, compensation, and conservative crash reconciliation, and a projector links successful writes into reviewed FB-004 state. Hardware profiles and artifact-store policy must be injected; machine-specific values and magic request flags/paths are not safe production interfaces.

#### No-Hardcoding Resource Admission

- Inject a validated `ResourcePolicy` and a live `ResourceSnapshot` from the selected runtime adapter. Represent capacities in one explicit base unit (bytes) and identify the resource domain (for example host memory, mapped-file residency, or device memory). Do not put `6144`, `1536`, or `350` MB defaults in the kernel.
- A 6 GB device limit or 1.5 GB PagedAttention cushion is an optional named profile value only when the selected backend actually exposes that resource and cache. It is not a platform-wide invariant. Missing or stale measurements fail closed for the operation that needs them; they do not fall back to a guessed ceiling.
- Admission reserves the requested budget atomically before work. Use a per-process synchronized lease/allocator so concurrent tasks cannot all pass against the same free capacity. Validate configured and requested values as finite, non-negative, and within representable limits. Releasing the lease in structured cleanup is authoritative; `gc.collect()` is not a memory-release guarantee and must not be used as a substitute for admission accounting.
- Inject fake resource providers and explicit budgets in tests. Assert exact boundary behavior, over-budget denial before worker invocation, concurrent reservation safety, and release on every exit path.

#### Two-Phase Receipts and Mutation Order

Keep FB-027 and FB-038 as local in-process authority interfaces. Their storage path, durability mode, and mutation target authorization come from explicit configuration and trusted scope, not hard-coded paths. JSONL may be a serialization choice, but does not imply a server or listener.

For a mutating intent, the order is:

1. Validate the typed intent, all four trusted scope fields, transaction identity/idempotency, and target authorization.
2. Acquire the resource lease. Pure validation and admission do not modify the target.
3. Persist and durably flush an immutable FB-027 `PREPARED` event containing enough transaction, scope, target, and prior-state/delta references to recover. If it cannot be persisted, deny before any worker side effect or target mutation.
4. Execute through the capability worker and FB-038 staging boundary; never write the target directly from a block. Run Block 6, then Block 8, and verify the staged result before commit.
5. FB-038 commits the authorized change. FB-027 appends a durable `OUTCOME` event only after verifying the committed state.
6. If any step after `PREPARED` fails, FB-038 compensates from recorded prior state/delta and verifies restoration. Append an immutable compensation outcome when possible. If restoration cannot be verified, return `INDETERMINATE`, never success, and block further mutations against the unresolved transaction/target until reconciliation.
7. Release the resource lease in `finally` on success, failure, or cancellation. No telemetry path may translate `INDETERMINATE` into success.

Receipts are append-only state transitions, not mutable status dictionaries: `PREPARED` -> `OUTCOME`, `COMPENSATED`, or `INDETERMINATE`. Enforce transaction uniqueness/idempotency and serialized state transitions within the process. A crash that leaves only `PREPARED` is unresolved, not success; recovery must inspect the durable journal and target state and compensate or reconcile before permitting a retry. If writing the terminal receipt itself fails, preserve the unresolved prepared state and surface an explicit failure; do not fabricate a durable terminal record.

#### Phase 2 Test Matrix

- Inject faults using fake receipt-store, worker, resource-provider, and mutation-authority implementations. Never accept `test_inject_fault` or a magic target path from an intent.
- Add PREPARED persistence failure (assert worker and mutation authority were never called), successful commit and durable OUTCOME, failed compensation with no success result, idempotent duplicate transaction handling, malformed/stale resource snapshots, concurrent admission, cleanup after cancellation/exception, and startup recovery of unresolved PREPARED events.
- Use a temporary isolated store and test targets supplied by fixtures. No machine-specific paths, hardware ceilings, target files, or provider labels live in production code.
